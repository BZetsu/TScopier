1. Executive summary

Plain English On 11 November at 10:28:54, one message — “Close all trades now” — was posted to a test channel that both production and staging follow. Staging closed the open trades. Production did nothing and reported “Must be a reply to the original signal”. The keyword rules read the message correctly in both places. The difference came from the AI that double-checks every message: it agreed with the rules on staging, but on production it misread the instruction as a cancel — and it was only 50 % sure. Because the wrong answer still looked like something the system could act on, the third, stronger reviewer (GPT-4o) was never called, and the coin-flip guess became the final answer. We fixed it by forcing the reviewer to run whenever the rules and the AI disagree, whenever the AI claims a cancellation the rules never saw, and whenever an actionable answer is under 70 % certain — plus two unbreakable rules written into the AI’s own instructions. The fix is deployed to staging and proven with live tests.

4. Root cause

  1. The rules engine scores management messages 0.92, but the fast-path threshold was 0.99 — so a plain “Close all trades now” always went to the AI for a final answer it did not need.
  2. The AI is not deterministic. Same message, two answers: close 0.95 on staging, cancel_pending 0.50 on prod.
  3. The reviewer had a hole. GPT-4o only ran when the AI was “uncertain” or blocked a trade the rules had parsed. cancel_pending counts as executable, so a 50 % guess became final with no second opinion — and there was no confidence floor.
  4. The executor then behaved correctly: a cancel that is not a reply cannot know which order to cancel, so it skipped with delete_pendings_requires_reply. The skip was honest; the misclassification upstream was the fault.
  5. Contributing: Cerebras (stage-2 provider) was returning HTTP 402 “payment required” on both environments, so every parse silently fell back to OpenAI.
Wider pattern The same hole produced the families in §3 — notably 91 messages in 30 days where BUY LIMITS GOLD @ … entry posts were read as cancellations and thrown away (same failure class as the documented 2026-09-19 incident).

5. The fix

Four coordinated changes (plus a complementary change already shipped by the performance workstream):

WhatExactly what it does
1Confidence floor
parseConfig.ts		 Any actionable AI answer below 70 % certainty must go to the reviewer instead of being trusted as final. Setting UNIVERSAL_PARSE_RECONCILE_MIN_CONF (default 0.70, clamped 0–1, safe on empty values) tunes it without code changes. Kills the 0.50-guess incident.
2Four review triggers
parseRouting.ts		 GPT-4o is now also called when: (a) rules and AI disagree on what kind of message it is; (b) the AI flips a trade’s direction (buy ↔ sell); (c) the AI claims a cancellation the rules never confirmed (the BUY LIMITS family); (d) any actionable answer is below the 70 % floor. Agreed, confident answers still skip the reviewer — normal traffic is unaffected.
3Two hard prompt rules
universalSignalParser.ts		 Written into both the AI’s and the reviewer’s instruction sheets: “close all / close everything / flatten” can only ever mean close, never a cancel; and a message that merely lists pending limit/stop entries with no cancel verb is an entry, never a cancellation.
4Standalone cancels act
managementExecutor.ts		 A parentless “cancel pending orders” now sweeps every resting pending order on the channel — broker-pending entries, resting LIMIT/STOP trades (each verified against the live broker list first, so a filled order can never be “cancelled”), and range legs. Per-account channel filters still apply; reply-scoped and order-linked cancels are unchanged; runs in bounded batches with an honest truncated flag.
+Complementary (performance workstream)
commit 5cd1580f		 Recognised management phrases now bypass the AI entirely and use the rules result directly — this alone closes the original incident at its source. Our four triggers guard everything that still reaches the AI.
