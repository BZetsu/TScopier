Basic-plan accounts silently discard every entry that carries a stop loss or take profit

Incident report · worker entry routing + admin board + Basic-plan defaults · 2026-11-18
SeverityHigh StatusFix implemented — deploy pending
DatesReported 2026-11-18 by Toky RAKOTOBE (029ab2db); root cause confirmed and reproduced the same day Affected4 accounts, 32 entry signals in 30 days
Componentworker/src/tradeExecutor/basketMerge/mergeRouting.ts, worker/src/tradeExecutor/entryPrepare.ts, src/lib/channelMessageFilters.ts Root causeA filter written for changes to existing trades is applied to new entries, before the code checks whether a trade exists

1. Executive summary (plain English)

What this incident is, in everyday terms:

  • A Basic-plan customer reported that none of his trades were opening. He had 20 messages from his signal channel and zero trades.
  • Every entry his channel sends includes a stop loss and a take profit. Our program reads the message correctly, then asks one question: does this message contain a stop loss or take profit? The answer is yes, so it treats the message as a request to change an existing trade.
  • His channel settings — filled in automatically by the product because he is on the Basic plan — say to ignore those changes. So the program skips the whole message, including the entry, and files it as "entry not opened".
  • It never checks whether he had an open trade. He had none, and never has.
  • Nothing was ever sent to his broker. That is why changing broker accounts made no difference, and why re-linking Telegram made no difference.
  • The one message he received without a stop loss went straight to the broker and was attempted. That is the proof: the stop loss in the message decided the outcome, not the broker.
  • Neither he nor our support team could see the setting. In his app the control is greyed out behind an upgrade prompt; in our admin dashboard it is not displayed at all.
  • We reproduced the defect four times on staging with four different symbols and prices, and confirmed it stops the moment the setting is switched to Allow.

4. Root cause

  1. The Basic plan sets every channel instruction category to ignore — src/lib/channelMessageFilters.ts:38-41, applied because channel_keyword_filters is Advanced-only (src/lib/planLimits.ts:116-118). The values are written when a channel is linked (src/lib/brokerChannelLink.ts:92-104) or configuration is saved (AccountConfigPage.tsx:2445-2447, :2562).
  2. The entry path reads those categories before it knows whether a trade exists — mergeRouting.ts:633-638 returns { handled: true, success: false }. The open-trade lookup is at line 641, seven lines later. Measured: zero database calls before the decision.
  3. The rule was written for a different job. f8b2ce57 (2026-05-27) added it to the modification-only path, where a trade always exists, and logged the skip. 954a9d00 (2026-06-12) added tryTeaserCompletionMerge, copied the guard, dropped the log line, and placed it before the anchor lookup.
  4. The failure is recorded without a reason — entryPrepare.ts:619-628 returns an outcome with no failureReason, so dispatch.ts:514-524 falls back to SKIP_REASON_ENTRY_NOT_OPENED, which reads like a broker or market problem.
  5. Nobody could see the setting. In the customer app the control is disabled and covered by an upgrade prompt (AccountConfigPage.tsx:4780, :4785-4791). The admin dashboard never reads the field: UserDetailPage.tsx:387 omits it from the query and ChannelBrokerConfigs.tsx:204-231 builds the Filters tab from manual settings only. A repository-wide search for channel_message_filters in tscopier-admin returns nothing.

5. The fix (implemented, not yet deployed)

  1. Prove an open basket before reading the filter. In tryTeaserCompletionMerge the channel filter is now consulted only after the anchor resolves, the anchor's parsed data is settleable, a live leg row exists for the anchor, and the ghost-basket check has cleared it. A new entry therefore never reaches the check, and the setting keeps its intended meaning: it still suppresses stop-loss and take-profit edits on trades that exist.
  2. Record every skip, with its own reason. The skip writes a merge_routed_modify_only row (status: skipped, payload reason channel_filter_ignored, anchor id, open leg count) and returns failureReason: 'basket_modify_skipped_by_channel_filter'. The separate reason matters: channel_filter_ignored is listed in NON_TRADE_SKIP_REASONS, which the customer log uses to hide keyword-filtered messages — reusing it would have hidden the skip and restored the original "no explanation" complaint.
  3. Carry the reason to the signal. entryPrepare.ts propagates it with the matching code. The parameter-follow-up path now returns the same reason instead of nothing.
  4. Bring the admin board to full parity with the customer app. Every stored setting is described, with anything unrecognised falling through to an "Other settings" section; the ten channel instruction categories are shown per channel; values matching the Basic preset are marked "set by plan default"; the layout is the app's vertical collapsible stack inside the existing closable modal, with a raw panel for the complete per-channel record.
  5. Tell Basic customers what is applied. The locked channel-filter control lists the categories applied automatically and states that entries still open, with an explicit empty state when nothing is ignored.

Why the first version of the guard move was not enough. The anchor is not proof of an open trade: resolveOpenBasketAnchorForParameterFollowUp falls back to resolveRecentEntrySignalAnchor, which selects recent signals in the same channel and direction within a 10-minute window while skipping only rows with status = 'skipped'. An earlier entry that failed as entry_not_opened has status = 'failed', so it qualifies as an anchor. A channel that re-posts a stopped entry within ten minutes would have been discarded again. The check now sits after the live-leg proof, and one of the tests covers exactly this case.
