1. Executive summary (plain English)

Plain English A customer spent the morning trying to link his Telegram account. It linked three times and was disconnected thirteen times in six minutes. The long list of identical “Telegram disconnected” lines in the admin is what alarmed support, and it is worth being precise about what those lines mean. Each one is produced by a call to the Disconnect action. A dropped connection never writes this line. In two of the bursts the calls arrived 4 times in 314 milliseconds and 8 times in 729 milliseconds — far faster than a person can press a button, so more than one client was acting at once.

We cannot yet name the client, because the logging that records the caller (IP address, browser, per-tab identifier) was switched on at 10:59 UTC, seventy-five minutes after his last attempt. The same pattern occurred on 17 November — three calls in 21 milliseconds — so this repeats, and it is not a one-off.

Two problems on our side made the aftermath worse. First, after the account was deliberately disconnected, the worker still tried to bring the listener back. Second, the status write that should have marked the account not linked was refused as stale ownership, so the admin kept saying linked while the database held no Telegram session at all. That mismatch is exactly what invites a customer to keep pressing Disconnect.

The account is now in a truthful state. Nothing was traded, no position was opened and no money is at risk. The customer needs to link once more, from a single tab, on a freshly loaded page.

4. Root cause (technical)

4.1 One writer, one row per call

telegram_link_disconnect is written only by disconnectTelegramSession (worker/src/sessionManager.ts, ~1303–1351). It is reached only through /auth/disconnect_telegram (worker/src/httpServer.ts:374), which the app calls from the Disconnect button (src/pages/dashboard/CopierEnginePage.tsx:373–397, 953–955) via the telegram-auth edge function. The edge function forwards with one fetch and no retry, and the client wrapper has no retry either, so N rows means N separate calls.

4.2 The bursts are not human input

4 calls in 314 ms, 8 calls in 729 ms, and 3 calls in 21 ms on 17 November. A connection drop never writes this event; drops appear in copier_listener_health (last_disconnected_at) and the connection trace.

4.3 Not attributable retrospectively

The telegram_auth_action trace (action, client id, IP, user agent) was deployed to production at 10:59 UTC, after the last call at 09:44. There are no trace rows for this user, so the responsible client(s) cannot be named from today's data. The next attempt will be attributable.

4.4 Worker defect A — reconnect after an intentional disconnect

At 09:42:25 the lease loop logged listener disconnected but renewing lease anyway … kicking reconnect in background for an account whose session had just been deleted. The reconnect cannot succeed (there is no session) and it races the disconnect.

4.5 Worker defect B — the "not linked" status write was refused

[copierHealth] upsert rejected (stale ownership) at 09:38:34 and 09:43:55. The disconnect path writes telegramAccountStatus: 'not_linked', but the write was refused, so the row kept telegram_account_status = 'linked' while telegram_sessions was empty. That is the state the app reads.

5. The fix

Applied immediately at 14:23 UTC — one row, no code:

update copier_listener_health
set telegram_account_status = 'not_linked',
    listener_status         = 'disconnected',
    copier_engine_status    = 'stopped',
    worker_ownership_status = 'unowned',
    mtproto_connected       = false,
    health_reason           = 'user_disconnected_telegram',
    updated_at              = now()
where user_id = '029ab2db-98ed-4abe-8704-5c09959b91b8';
Still open
  1. Make /auth/disconnect_telegram idempotent and debounced, so repeated calls collapse into one operation and one row.
  2. Do not reconnect a listener whose session was deleted on purpose — the lease loop must respect a deliberate stop.
  3. Let the disconnect health write succeed without a lease, so not_linked always lands.
  4. Consider an admin action “reset Telegram state” that clears session, pending auth, leases and health in one step.
