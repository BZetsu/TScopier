1. Executive summary (plain English)

Plain English Throughout the morning of 19 November, trades stopped opening for a growing number of customers, one broker at a time. Every affected account still showed as connected, signals were received and understood correctly, and the copier tried to place each order — but the broker refused all of them. The refusal was not about trading rules. It happened one step earlier: the small bridge service that connects us to the brokers was running a two-month-old version of the MetaTrader connection software. MetaQuotes periodically raises the minimum version brokers accept, and each broker switches that on at its own time. Once a broker switched, every order for its accounts was refused with OLD_VERSION. Customers only saw “No position opened”, which looks like a problem with the signal or with their account. Nothing on the account was wrong: no trade was placed, nothing was left open, no money was at risk. The incident ran from 02:16 to 10:15 UTC and cost 58 signals across 18 customers on 27 MT5 accounts. It stopped within a minute of updating the bridge to the current build: the first connection test returned OK instead of OLD_VERSION, and eight trades opened on previously failing accounts between 10:24 and 10:30.

This had nothing to do with the September “no position opened” bug, which was a parsing problem triggered by edited Telegram messages. Here the order was built correctly and refused by the bridge.

4. Root cause

mt5rest does not run a MetaTrader terminal. It is a .NET REST wrapper that logs in to each broker’s trade server through the MT5 Manager API. The bridge’s own stack trace is the proof — the failure is at Connect(), not at order send:

[10:06:38 WRN] <OLD_VERSION> mtapi.mt5.ServerException: OLD_VERSION at mtapi.mt5.MT5API.Connect() at mt5rest.MyControllerBase.GetClient(String id, String method, Boolean checkConnect) MyControllerBase.cs:line 253 at mt5rest.Connection.CheckConnect(String id) Controllers/Connection.cs:line 1903

The running container was built from the 10 September image (vendor tag 26.09.10-15.08; /app files dated 10 Sep 19:08). The vendor has published newer builds since, including ten on 19 November alone (26.11.19-05.02 … 26.11.19-09.26) — that is how they ship updated Manager API clients. Brokers raise the minimum accepted build in waves, which is why the failures arrived one broker at a time and why no account recovered on its own.

Across all 27 accounts there are zero successful orders after the first OLD_VERSION, and the accounts stayed connected throughout: an out-of-date Manager API still logs in far enough to stream prices and report balances, and only refuses trading.

Why it stayed invisible for eight hours

  1. The customer-visible reason is the generic entry_not_opened; the raw bridge string appeared only as the technical code.
  2. mtapi_accounts_error and mtapi_connect_errors measure the account connection columns, which stayed connected.
  3. executions_failing reached only its warning threshold at 08:55 — after six hours and dozens of lost signals — and warning recipients are not paged.

5. The fix

Operational (applied on the VPS)

  1. docker pull timurila/mt5rest → image created 2026-11-19T09:27:01Z (26.11.19-09.26).
  2. Recreated the container through the redactor installer, preserving the UserKey licence env, the 127.0.0.1:8080 binding, the unless-stopped restart policy and the password-redacting entrypoint:
    cd /root/mtapi-log-redactor CONTAINER=mtapi IMAGE=timurila/mt5rest HOST_IP=127.0.0.1 HOST_PORT=8080 CONTAINER_PORT=80 bash ./install.sh
  3. Verified at the bridge: curl -s "http://127.0.0.1:8080/CheckConnect?id=<session>" → OK (previously 201 with an OLD_VERSION body).

Code (this repository)

  • supabase/functions/alert-evaluator/index.ts — new evalMtapiOldVersion, its dispatch case, the threshold documentation line and a NEXT_ACTION runbook. It fires on the first affected account (max_accounts: 0): OLD_VERSION has no benign cause, nothing self-heals, and this incident's first 24 minutes were a single account before the rest followed. max_rows: 6 covers rows without an account id, and persistence_minutes: 5 stops a quiet ten-minute gap from resolving the event, emailing “recovered” and then muting the re-fire under the cooldown.
  • supabase/migrations/20261119120000_mtapi_old_version_alert.sql — adds the mtapi_old_version rule: critical, {"max_accounts": 0, "max_rows": 6, "persistence_minutes": 5}, 10-minute window, 900 s cooldown.
Deploy order Deploy alert-evaluator before applying the migration, or the rule is skipped as “no evaluator for rule”.

9. Follow-ups

  1. Pin the image and refresh it deliberately. The container was recreated on 14 Nov with a stale local latest from September. Run a pinned tag and pull a newer build monthly; surface the image creation date in Systems Health.
  2. Deploy the new rule (evaluator first, then migration) and confirm it fires by threshold-testing against historical rows.
  3. Log rotation on the Docker daemon (max-size/max-file) — docker logs --since 12h had to be interrupted because the json-file had grown so large.
  4. Reconcile the nginx internal token: /root/.mtapi_internal_token no longer matches map $http_x_internal_token, so verification calls using the file get 403. The worker is unaffected (it authenticates with the Bearer key).
  5. No replay of the 58 lost signals — the entries are hours old and re-entering them at current prices is worse than no trade. Customer communication was left to support.
