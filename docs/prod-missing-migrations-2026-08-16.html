What each missing migration does

1. 20260810000000_trade_reports — HIGH priority (live bug)

Plain English: Creates the trade_reports table — the queue where users file complaints about trades (“wrong entry”, “wrong SL/TP”, “not executed”, etc.) for support staff to review. Both reporting paths insert into this table:

  • The manual “Report” button in the trade detail modal (src/components/trades/ReportTradeModal.tsx — client-side INSERT).
  • The in-app assistant report_trade tool (supabase/functions/assistant-chat/index.ts).

What it creates: - trade_reports table: user_id, trade snapshot (symbol, direction, ticket, broker_label, entry_price, sl, tp, lot_size), category, reason, status (open/resolved), timestamps. - Row Level Security: users can insert/view only their own reports. - Indexes on (user_id, created_at) and (status).

Impact without it: Any attempt to file a trade report fails with ERROR 42P01: relation "trade_reports" does not exist. This is a live, user-facing defect on prod.

2. 20260816000000_trade_reports_signal_id — HIGH priority

Plain English: Adds a signal_id column so reports stay traceable back to the originating signal — including reports on skipped / non-actionable trades that have no symbol or ticket (which the assistant can now file).

What it creates: - trade_reports.signal_id (nullable, backwards compatible). - Index trade_reports_signal_idx on signal_id.

Impact without it: Once #1 is applied, reports still work — they just can’t link to a signal. This column is required for the assistant’s skipped-trade reporting fix to function correctly.

3. 20260730120000_layering_modes_foundation — MEDIUM (dormant feature)

Plain English: Prepares the range_pending_legs table (the ladder of pending orders for range trades) for future “static/dynamic” layering modes, where the ladder is planned up-front instead of built the legacy way. This migration only adds empty columns — existing rows are untouched and keep behaving exactly as before.

What it creates: - range_pending_legs.layer_plan_id (text, nullable). - range_pending_legs.layer_plan_metadata (jsonb, nullable). - Partial index on layer_plan_id.

4. 20260731120000_layering_plans — MEDIUM (dormant feature)

Plain English: Creates the layering_plans table — the “blueprint” for static/dynamic range-layering ladders (mode, status lifecycle, frozen calculator metadata, semantic fingerprint), plus the activate_layering_plan function that materializes plans into executable legs. Adds many nullable columns to range_pending_legs and unique indexes preventing duplicate ladder steps. Pure additive — nothing executes Static/Dynamic until Phase D ships, and the feature is behind kill-switch flags (LAYERING_MODES_EXECUTION_ENABLED, LAYERING_MODES_PREPARE_ONLY) restricted to staging allowlisted accounts.

What it creates: - layering_plans table (service-role only; no client access). - activate_layering_plan(...) function + layering-settings guard triggers. - Unique indexes: (signal_id, broker_account_id, basket_key, mode), (layer_plan_id, step_idx) on range_pending_legs, (broker_account_id, broker_client_reference). - 17 additive nullable columns on range_pending_legs (broker_client_reference, native_submission_status, submission_claimed_at, cancellation_*, reconciliation_*, etc.).

Dependency: requires #3 first (its unique index on range_pending_legs(layer_plan_id, step_idx) needs the layer_plan_id column).

Relevance to the codebase

These migrations exist because the worker (worker/) already implements the static/dynamic layering execution path and reads/writes these tables. Without the migrations, the following modules fail at runtime or at typecheck against the schema.

What consumes migration 3 (foundation columns)

range_pending_legs.layer_plan_id and .layer_plan_metadata are the link between an executed leg and the immutable plan that produced it:

  • worker/src/manualPlanning/layeringPlanPersistence.ts — the persistence layer: inserts rows into layering_plans, reads a plan back by layer_plan_id, and calls the RPC activate_layering_plan to materialize funded legs. It compares data.layer_plan_id !== snapshot.planId and writes layer_plan_id on every materialized range_pending_legs row.
  • worker/src/layeringPlanLifecycle.ts — drives a plan through its status lifecycle (prepared → activating → active → entries_complete/completed, or cancelled) and resolves each leg via range_pending_legs(layer_plan_id).
  • worker/src/manualPlanning/layeringModes.ts — the calculator/constants (LAYERING_MODES, DEFAULT_STATIC_LAYER_COUNT, DEFAULT_DYNAMIC_STEP_PIPS, LAYERING_PLAN_SCHEMA_VERSION); its output is frozen into layer_plan_metadata exactly as the migration’s comment describes.

What consumes migration 4 (layering_plans table + range_pending_legs additions)

The layering_plans table + the 17 new range_pending_legs columns (broker_client_reference, native_submission_status, submission_claimed_*, reconciliation_*, cancellation_*, …) back the broker-native pending-order engine:

  • worker/src/tradeExecutor/layeringModeBrokerPending.ts — the submit/claim/confirm path: writes broker_client_reference and transitions native_submission_status through planned → submission_claimed → confirmed, querying range_pending_legs on broker_client_reference and native_submission_status. This is the code the range_pending_legs_broker_client_ref_idx unique index protects.
  • worker/src/rangeBrokerPendingMonitor.ts + rangeBrokerPendingHelpers.ts — sweeps broker-native pendings; relies on submission_claimed_* / reconciliation_* columns for durable claiming.
  • worker/src/tradeExecutor/layeringModeBrokerPendingRecovery.ts — restart recovery parses persisted layer_plan_metadata instead of re-running calculators (the exact property the runbook calls out).
  • worker/src/tradeExecutor/orderLegExecution.ts — the onImmediateFill hook fires layering_first_fill_activation (dynamic first-fill gating), which calls into activate_layering_plan.
  • worker/src/virtualPendingMonitor.ts — materializes virtual pendings into range_pending_legs and marks category: 'layering' events on failure.

Bottom line: migrations 3 & 4 are not speculative — they are the schema backing for worker code already merged in this repo (staging). Staging has them; prod does not, so any staging-validated layering rollout would be broken on prod the moment it is enabled.
