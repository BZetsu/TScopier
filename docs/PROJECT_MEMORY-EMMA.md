### 2026-08-13 - Telegram Login-Code Resend/Fallback Incident

- **Incident:** Production evidence showed `auth.SendCode` was definitely invoked and Telegram returned success with delivery `app`, but at least three users did not see a Telegram login code in their Telegram app. Repeating the request created a fresh `sendCode` request and fresh `phoneCodeHash`, and pending auth eventually expired. A malformed earlier phone input correctly surfaced `PHONE_NUMBER_INVALID`.
- **Root architectural gap:** The phone auth flow treated every retry as a new `auth.SendCode` attempt. It retained only `phoneCodeHash` plus broad delivery and discarded Telegram `auth.SentCode.next_type`, `timeout`, and code length metadata. There was no `auth.resendCode` implementation, so the UI could not follow Telegram's documented "wait timeout, then resend with the existing hash" fallback path.
- **Fix implemented:** Added a minimal pending phone auth state model that keeps the current server-only `phoneCodeHash`, current delivery, `next_type` mapped to safe UI delivery metadata, timeout-derived `resendAvailableAt`, and code length. The metadata is stored inside the existing short-lived `telegram_auth_pending.auth_session_string` envelope for phone auth rows, avoiding migrations and keeping QR auth rows compatible.
- **Resend behavior:** Added worker `/auth/resend_code`, Edge action `resend_code`, shared frontend typing, and dashboard/onboarding resend actions. Before Telegram's timeout expires, resend is rejected locally with the remaining wait. After timeout, the worker calls `Api.auth.ResendCode` using the existing phone number and current server-side hash, consumes the returned `auth.SentCode`, and replaces the old hash with the returned hash as the single authoritative hash.
- **UX behavior:** The code screen now shows Telegram app/call-aware guidance and a countdown-gated "Request another delivery method" button. SMS/call fallback language is shown only when Telegram returns a matching `next_type`; the app does not promise SMS by default.
- **Security/privacy:** Frontend responses never include `phoneCodeHash`. Incoming `phone_code_hash` and `session_string` remain stripped at the Edge proxy. Auth logs redact raw phone numbers to a stable hash and redact code/hash/session/password/token-like fields. No phone number, OTP, auth key, session string, API hash, password, or token was logged intentionally or documented.
- **CodeSettings audit:** Current GramJS `Api.CodeSettings` remains unchanged: `allowFlashcall=false`, `currentNumber=true`, `allowAppHash=true`. Telegram docs indicate `current_number` is ignored unless flash calls are enabled, and `delivery=app` is Telegram's server-selected delivery method. No evidence proved these flags caused missing app notifications, so they were not changed.
- **Listener/channel incident:** Production also showed GramJS update-loop timeout and listener/channel polling failures. This fix does not touch listener recovery, channel polling, trade execution, XAUUSD, range trading, broker errors, cache behavior, migrations, QR routing, or copier health semantics. Treat "connected but channels spin forever" as a separate follow-up incident unless staging proves it is tightly coupled to auth.
- **Tests / validation:** Added focused worker tests for resend wait, `auth.ResendCode` use, returned-hash replacement, verify using the latest hash, delivery/next_type/timeout capture, conservative timeout fallback, safe response shape, redacted logs, and deterministic Telegram auth error messages. Passed targeted worker tests, worker build, root build, and targeted ESLint for changed worker/shared component/edge files. Full repo ESLint still fails on unrelated existing lint debt in backoffice, dashboard/onboarding large pages, Supabase functions, and worker modules.
- **Files changed:** `worker/src/authService.ts`, `worker/src/authService.resend.test.ts`, `worker/src/authService.redaction.test.ts`, `worker/src/httpServer.ts`, `worker/src/httpServer.authErrors.test.ts`, `supabase/functions/telegram-auth/index.ts`, `src/lib/telegramAuthApi.ts`, `src/components/telegram/TelegramConnectFlow.tsx`, `src/pages/dashboard/CopierEnginePage.tsx`, `src/pages/onboarding/steps/TelegramLinkStep.tsx`, generated `dist/*`, generated `worker/dist/*`, and `docs/PROJECT_MEMORY-EMMA.md`.

Verify initial delivery `app`, countdown, no Telegram call before timeout, `auth.resendCode` after timeout, delivery changing when Telegram offers a fallback, latest hash verification, 2FA/password flow, QR unaffected, and no sensitive auth values in logs/Sentry.

### 2026-08-12 - Deferred-Only Range Plan Registration Incident

- **Incident:** An Aug 11-style manual multi/range BUY allocation could produce a valid plan with zero immediate broker orders and one deferred range leg. The executor incorrectly treated that plan as empty because it checked only immediate orders before pending-leg registration. The user-facing result could look filtered/skipped even though the planner had produced a valid waiting/deferred leg.
- **Root cause:** `worker/src/tradeExecutor/entryPrepare.ts` had an empty-plan guard of `if (plan.orders.length === 0)`. That guard runs before `plan.virtualPendings` are copied, capped, materialized, and handed to the deferred trigger path. Therefore `orders=[]` and `virtualPendings=[...]` was rejected before `materializeVirtualPendingLegs(...)` could insert `range_pending_legs`.
- **Invariant:** A range plan is empty only when both immediate broker orders and deferred/waiting legs are empty. `orders.length === 0` alone means "no immediate broker order now"; it does not mean "no execution work".
- **Exact fix:** The guard now computes `const plannedVirtualPendings = plan.virtualPendings ?? []` and skips only when `plan.orders.length === 0 && plannedVirtualPendings.length === 0`. The later virtual list is sliced from the same planned array, preserving existing capping behavior.
- **Planner status:** The planner was correct. `planMultiManualOrders(...)` already had the combined `orders.length === 0 && virtualPendings.length === 0` fallback and can intentionally emit zero immediates plus deferred range legs for 100% range allocation.
- **Execution status after fix:** Deferred-only plans now proceed through normal `runRangeEntry(...)` materialization. `sendImmediateLegs(...)` already treats zero immediate legs as handled when virtual materialization or strict pending placement succeeded, so the downstream status contract did not need a parallel state.
- **Status/logging behavior:** A successfully registered deferred-only range plan is no longer logged through `logSendSkipped(..., 'filtered')` just because no immediate position opened. It uses the existing `virtual_pending_inserted` / pending terminology and returns `openedOrMerged: true` from the executor outcome after materialization.
- **Tests added:** Added planner regressions for 100% BUY range and equivalent SELL range producing `orders=[]` plus one virtual leg. Added `worker/src/tradeExecutor/deferredOnlyRangePlan.test.ts` covering BUY and SELL deferred-only registration without broker `OrderSend`, truly empty plan skip preservation, pending row shape (`status='pending'`, side, anchor, trigger), and trigger-side correctness for the existing virtual pending monitor machinery.
- **Guard audit:** Other immediate-empty guards were reviewed. `orderLegExecution.ts` already has the correct zero-immediate success behavior when `materializedVirtuals || strictBrokerPlaced`. `strictEntryPending.ts` requires capped immediates because it aggregates strict-entry broker pending orders, not range virtuals. The planner guard already checks both lists.
- **Downstream cleanup blocker found in final audit:** `worker/src/rangePendingBasketCleanup.ts` still treated `trades.status IN ('open', 'pending')` returning zero rows as proof that the basket was closed. That was valid for a basket that had already opened and then flattened, but invalid for deferred-only range plans because they intentionally have no immediate `trades` row while `range_pending_legs.status='pending'` is waiting for the monitor.
- **Cleanup root cause:** `reconcileBasketFlatFromBroker(...)` called `purgeRangePendingLegsIfBasketFlat(..., 'signal_closed')` when `openRows.length === 0`. The virtual pending monitor runs broker-flat reconciliation on its first tick, so a freshly inserted deferred-only row could be deleted before the price reached its trigger.
- **Active pending liveness invariant:** A signal/broker basket is active when it has open/pending trade rows, or active range pending rows, or another existing deferred execution state. For range pending rows the active statuses are exactly `pending`, `claimed`, and `broker_pending`. Terminal/non-liveness statuses include `fired`, `expired`, `cancelled`, and `failed`.
- **Exact cleanup fix:** `worker/src/rangePendingLegDelete.ts` now exports `ACTIVE_RANGE_PENDING_LEG_STATUSES` and checks active `range_pending_legs` scoped by `signal_id + broker_account_id` before flat-basket deletion. If there are no open/pending trades but an active range pending leg exists and no closed trade history exists for that same signal/account, cleanup returns without deleting it. If closed trade history exists, the prior flat-basket purge behavior is preserved so old active leftovers do not become immortal. `reconcileBasketFlatFromBroker(...)` now returns `null` when that liveness guard preserves the basket instead of reporting `signal_closed`.
- **Multi-account behavior:** The liveness and purge checks are scoped to the same `signal_id + broker_account_id` pair used by pending rows and dispatch claims. Cleanup for a closed broker account can delete that account's stale rows without touching another broker account's active deferred-only row for the same signal.
- **Deferred-only lifecycle after cleanup fix:** A BUY or SELL range plan with `orders=[]` and one active virtual pending now passes entry preparation, inserts a `range_pending_legs` row, survives the monitor's first reconciliation tick, remains eligible for the existing CAS claim path, and later fires through the existing virtual pending monitor when bid/ask crosses the trigger.
- **Additional tests:** Added cleanup regressions for zero trade rows plus active pending preserving the row, BUY and SELL deferred-only first-reconcile survival, zero trade rows plus no active pending purging stale state, terminal statuses not counting as active liveness, open trade plus pending preserving existing behavior, fired/materialized rows not keeping a dead basket alive, closed trade history allowing active leftovers to purge, multi-account isolation, two deferred-only accounts remaining isolated, and terminal-vs-active mixed account behavior.
- **Scope isolation:** No changes were made to range allocation percentages, lot splitting/rounding, pip math, XAUUSD conventions, SL/TP calculation, broker execution, or deferred trigger pricing.
- **Remaining risks:** This was validated with focused local tests and mocked execution context, not staging traffic. Full CI/staging should still verify live-fast pipeline summaries and UI copy for pending-only outcomes. Signal status may still read as executed/handled while a virtual pending is waiting; this is compatible with duplicate-dispatch prevention and monitor execution, but the wording remains UX debt. No production connection, migration, deploy, push, commit, or trade was performed.

### 2026-08-10 - Telegram Malformed RPC Recovery Exhaustion

- **Branch:** `fix/telegram-recovery-user-errors`.
- **Production Sentry incident:** `telegram_recovery_exhausted` and `telegram_listener_failed` were observed together with reason code `GRAMJS_MALFORMED_RPC_RESULT` and message `Malformed Telegram RPC result recovery exhausted`.
- **Root cause:** The current malformed-RPC path in `worker/src/userListener.ts` counted GramJS malformed RPC results but did not perform real recovery until the counter exceeded the window limit. On exhaustion it treated the condition like AUTH_KEY recovery exhaustion by calling the auth-key invalidation callback, which could invalidate a still-valid Telegram session. Malformed RPC is a GramJS/MTProto transport or decoder failure signal, not proof that the persisted auth session is invalid.
- **Likely contributing conditions:** Existing incident docs point to GramJS BinaryReader malformed-body failures, update-loop transport state problems, reconnect races, and Telegram flood-wait/poll pressure. This change does not prove whether the originating malformed body was Telegram-side, network truncation, or GramJS state corruption; it fixes the unsafe local recovery behavior.
- **Recovery path after fix:** `client.onError` routes `GRAMJS_MALFORMED_RPC_RESULT`, `readUInt32LE`, and `Cannot read properties of undefined` to `noteMalformedRpcResult`. That path now marks recovery intent, joins the existing reconnect singleflight, disconnects, recreates the MTProto client when the listener owns the client instance, reuses the current saved session string, reconnects, requires a successful `updates.GetState` probe, then restores channel subscriptions and recent catch-up through the existing `forceReconnect` path.
- **Fix:** `worker/src/userListener.ts` now attaches the GramJS error handler through a reusable method so recreated clients keep the same handler. Malformed RPC calls `requestReconnect('malformed_rpc_result')` instead of only logging. `forceReconnect` snapshots the session before disconnect, recreates the client for malformed-RPC recovery when safe, probes before setting `isConnected=true`, resets malformed-RPC counters only after successful recovery, and never calls Telegram session invalidation for malformed RPC exhaustion.
- **Blocker follow-up:** Final safety audit found that owned-client recreation disconnected the old client before replacement but did not explicitly detach the current NewMessage/EditMessage handlers from the captured old client before `this.client` was reassigned. If GramJS kept dispatching after a failed or incomplete disconnect, duplicate signal processing was possible. The fix now captures `oldClient`, removes both current handlers from that explicit old client, clears handler references, then disconnects and only then creates/assigns the replacement client. Invariant: old Telegram client handlers must be detached before client replacement.

### 2026-08-07 - Staging Light Channel Config Cache

- **Branch:** `perf/light-channel-config-cache`.
- **Objective:** Implement the approved staging-first light configuration cache for the trade dispatch path. The goal is to reduce repeated Supabase reads for stable channel/account configuration without changing trade logic, XAUUSD pip logic, observability/copier-health semantics, durable claims, idempotency, broker readiness, or broker-send authority.
- **Original pre-broker DB-read path:** After a signal is accepted, `TradeExecutor.handleSignal` ensures the `signals` row exists, applies in-process duplicate protection, checks copier pause/subscription/broker eligibility, resolves channel metadata, and selects eligible brokers from the in-memory broker cache. For each broker, `sendOrder` first checks whether channel config is ready from cached broker state, then force-refreshes `broker_channel_trading_configs` through `fetchFreshBrokerForChannel(...)` before `withChannelTradingConfig(...)`, durable `claimSignalBrokerDispatch(...)`, and broker execution. Other live reads around this path include execution proof (`trades`, `signal_range_entry_waits`, `trade_execution_logs`), materialization/idempotency probes, range wait reads, and post-send signal finalization reads.
- **Read classification:** The repeated `broker_channel_trading_configs` row read is safe to cache briefly because it contains stable per-channel copier/manual/risk/layering/AI settings. `broker_accounts` are already cached in memory from startup + realtime. `telegram_channels` metadata is already cached by `channelMetaCache` and invalidated on channel updates. Copy-limit state already has its own short cache and was not moved into this feature. Durable claims, execution proof, idempotency/materialization checks, broker order state, current prices, open orders, broker connectivity/readiness, balance/equity/margin, kill switches, cancellation/reconciliation state, listener health ownership, and already-sent decisions remain explicitly excluded and live.
- **Implementation:** Added `worker/src/lightConfigCache.ts`, an in-memory per-worker cache around the pre-send `broker_channel_trading_configs` lookup. `LIGHT_CONFIG_CACHE_ENABLED=false` keeps the legacy database lookup path. When enabled, cache misses/expiry fetch the authoritative DB row, store a versioned entry, and apply the row to the broker before normal config resolution. Cached payloads are limited to the config row and recursively strip credential-like keys before storage. The final audit blockers were fixed before approval: stale in-flight fills are discarded after invalidation, invalidation uses structured exact identity instead of substring matching, and cache memory is bounded.
- **Entry shape / key:** Entries use `{ schemaVersion: 1, cachedAt, expiresAt, configVersionOrUpdatedAt, data }`, where `configVersionOrUpdatedAt` comes from `broker_channel_trading_configs.updated_at` when present. That field is informational only; it does not prevent stale writes. The stale-fill guard is the per-key generation/epoch. Keys are built from exact structured `{ userId, channelId, brokerAccountId }` identity with normalized channel ids and contain no secrets.
- **TTL / flags:** Defaults are `LIGHT_CONFIG_CACHE_ENABLED=false`, `LIGHT_CONFIG_CACHE_TTL_MS=5000`, and `LIGHT_CONFIG_CACHE_MAX_ENTRIES=1000`. Invalid TTL values fail safely by disabling cache use and reporting effective TTL `0`. Invalid max-entry values fall back to the safe default. Staging enablement requires setting `LIGHT_CONFIG_CACHE_ENABLED=true`, `LIGHT_CONFIG_CACHE_TTL_MS=5000`, and optionally keeping `LIGHT_CONFIG_CACHE_MAX_ENTRIES=1000`. Production must remain disabled until staging results are reviewed.
- **Invalidation:** `TradeExecutor.subscribeChannelTradingConfigs()` invalidates affected cache identities on `broker_channel_trading_configs` realtime before refreshing the existing broker cache. `INSERT` invalidates the new identity, `DELETE` invalidates the old identity, and `UPDATE` invalidates both old and new identities so broker/channel changes cannot leave the old cache key alive. When the broker owner is known in memory, invalidation is exact user+channel+broker; otherwise it falls back to a bounded structured broker+channel scan of known identities. No new Redis/pubsub subsystem was added; realtime invalidation plus the 5s TTL bounds staleness.
- **Stale-fill protection:** Each key has a generation counter. A DB fetch captures the current generation before it starts. Invalidation increments the generation and removes that key from the join map. If the old fetch later resolves, the caller may receive the DB result to preserve legacy semantics, but the result is not stored in cache and `light_config_cache_stale_fill_discarded` is counted. Newer generation fetches may populate normally, and failed fetches clear in-flight state.
- **Fallback behavior:** Valid hits use cached stable config. Misses, expired entries, malformed entries, invalid TTL, and disabled cache fetch DB. Cache subsystem errors are counted and bypassed; the wrapper falls back to the DB fetch. If the underlying authoritative DB lookup behaves as a no-row/no-update fallback, that existing behavior is preserved.
- **Safety boundaries:** The cache does not replace `ensureSignalRow`, `signalExecutionProven`, `manualDispatchAlreadyMaterialized`, `claimSignalBrokerDispatch`, broker session/readiness checks, broker symbol/quote/order calls, range wait state, cancellation state, reconciliation state, or post-send persistence. Cache failure must never stop trading/listening by itself, but required underlying DB failures preserve existing semantics.
- **Concurrency / memory:** The cache uses per-key singleflight. Concurrent identical user+channel+broker lookups await the same DB promise unless invalidation advances the generation; unrelated keys do not serialize. Completed and failed promises are removed. Entries are capped by `LIGHT_CONFIG_CACHE_MAX_ENTRIES` using deterministic recency/order eviction, and expired cold entries are pruned on get/set/invalidate without a high-frequency timer. At 50 users the default cap should be comfortably below limit for typical channel/account counts; at 500 users the hot set remains bounded; at 5,000 users hit rate may fall, but per-worker memory remains capped at 1000 entries unless explicitly tuned.
- **Metrics:** Added low-noise worker metrics for `light_config_cache_hit`, `light_config_cache_miss`, `light_config_cache_expired`, `light_config_cache_invalidated`, `light_config_cache_fallback_db`, `light_config_cache_malformed`, `light_config_cache_error`, `light_config_cache_singleflight_join`, `light_config_cache_stale_fill_discarded`, `light_config_cache_evicted`, `light_config_cache_pruned`, plus histogram-compatible lookup, cached-lookup, and DB-fallback duration metrics. Cache hit/miss/expiry does not emit Sentry issues.
