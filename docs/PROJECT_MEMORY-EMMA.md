### 2026-08-10 - Telegram Malformed RPC Recovery Exhaustion

- **Branch:** `fix/telegram-recovery-user-errors`.
- **Production Sentry incident:** `telegram_recovery_exhausted` and `telegram_listener_failed` were observed together with reason code `GRAMJS_MALFORMED_RPC_RESULT` and message `Malformed Telegram RPC result recovery exhausted`.
- **Root cause:** The current malformed-RPC path in `worker/src/userListener.ts` counted GramJS malformed RPC results but did not perform real recovery until the counter exceeded the window limit. On exhaustion it treated the condition like AUTH_KEY recovery exhaustion by calling the auth-key invalidation callback, which could invalidate a still-valid Telegram session. Malformed RPC is a GramJS/MTProto transport or decoder failure signal, not proof that the persisted auth session is invalid.
- **Likely contributing conditions:** Existing incident docs point to GramJS BinaryReader malformed-body failures, update-loop transport state problems, reconnect races, and Telegram flood-wait/poll pressure. This change does not prove whether the originating malformed body was Telegram-side, network truncation, or GramJS state corruption; it fixes the unsafe local recovery behavior.
- **Recovery path after fix:** `client.onError` routes `GRAMJS_MALFORMED_RPC_RESULT`, `readUInt32LE`, and `Cannot read properties of undefined` to `noteMalformedRpcResult`. That path now marks recovery intent, joins the existing reconnect singleflight, disconnects, recreates the MTProto client when the listener owns the client instance, reuses the current saved session string, reconnects, requires a successful `updates.GetState` probe, then restores channel subscriptions and recent catch-up through the existing `forceReconnect` path.
- **Fix:** `worker/src/userListener.ts` now attaches the GramJS error handler through a reusable method so recreated clients keep the same handler. Malformed RPC calls `requestReconnect('malformed_rpc_result')` instead of only logging. `forceReconnect` snapshots the session before disconnect, recreates the client for malformed-RPC recovery when safe, probes before setting `isConnected=true`, resets malformed-RPC counters only after successful recovery, and never calls Telegram session invalidation for malformed RPC exhaustion.
- **Blocker follow-up:** Final safety audit found that owned-client recreation disconnected the old client before replacement but did not explicitly detach the current NewMessage/EditMessage handlers from the captured old client before `this.client` was reassigned. If GramJS kept dispatching after a failed or incomplete disconnect, duplicate signal processing was possible. The fix now captures `oldClient`, removes both current handlers from that explicit old client, clears handler references, then disconnects and only then creates/assigns the replacement client. Invariant: old Telegram client handlers must be detached before client replacement.
- **Files changed:** `worker/src/userListener.ts`, `worker/src/sessionManager.shutdown.test.ts`, `worker/src/copierHealth.ts`, `worker/src/copierHealth.test.ts`, `docs/copier-health-model.md`, `docs/sentry-business-observability.md`, and `docs/PROJECT_MEMORY-EMMA.md`.
- **Tests:** Focused tests cover malformed RPC triggering recovery, concurrent malformed errors joining the same reconnect, valid session preservation, successful recovery after reconnect/probe, probe-required recovery, recovery exhaustion without auth invalidation, old message/edit handler detachment before client replacement, disconnect failure leaving no old handlers registered, repeated malformed recoveries not accumulating handlers, shutdown during cleanup leaving old handlers detached, malformed exhaustion Sentry dedupe, auth-invalid behavior remaining distinct, copier-health recovery semantics, session shutdown/lease behavior, GramJS malformed-body patching, Telegram auth recovery helpers, business-event dedupe/redaction, Sentry redaction, targeted ESLint, and worker build.
- **Health behavior:** During malformed-RPC recovery the listener is reconnecting/degraded and is not falsely operational. Successful recovery requires a successful Telegram probe before returning to operational. Exhausted malformed-RPC recovery marks the listener failed/offline while keeping the Telegram account linked. Reconnect-required is reserved for proven auth/session invalidation.
- **Sentry behavior:** The duplicate incident pair was one underlying malformed-RPC recovery incident emitted twice. After this fix, malformed-RPC exhaustion emits `telegram_recovery_exhausted` with `GRAMJS_MALFORMED_RPC_RESULT`; the health transition remains persisted but does not also emit `telegram_listener_failed` for the same incident. Generic reconnect exhaustion still uses `telegram_listener_failed`.
- **Remaining risks:** The originating malformed RPC body cause remains unproven without production packet-level evidence. Recreating the client is skipped for adopted auth-time clients, where the listener does not own construction. Deferred retry behavior still depends on existing reconnect backoff settings. Full CI and staging soak are still required before production.
- **Rollback:** Revert this code change to return to prior behavior. Operationally, a rollback may reintroduce malformed-RPC session invalidation and duplicate Sentry issue emission; no database migration or cleanup is involved.
- **Invariants:** Do not clear or rotate persisted Telegram sessions for malformed RPC alone. Do not log session strings, phone numbers, auth keys, OTPs, raw Telegram messages, or tokens. Keep AUTH_KEY_UNREGISTERED/AUTH_KEY_DUPLICATED distinct from malformed RPC. Keep reconnect singleflight and worker ownership health CAS intact. Do not modify broker symbol handling, XAUUSD pip logic, trade execution, light config cache, migrations, deployment, or production service connections as part of this fix.

### 2026-08-07 - Staging Light Channel Config Cache

- **Branch:** `perf/light-channel-config-cache`.
- **Objective:** Implement the approved staging-first light configuration cache for the trade dispatch path. The goal is to reduce repeated Supabase reads for stable channel/account configuration without changing trade logic, XAUUSD pip logic, observability/copier-health semantics, durable claims, idempotency, broker readiness, or broker-send authority.
- **Original pre-broker DB-read path:** After a signal is accepted, `TradeExecutor.handleSignal` ensures the `signals` row exists, applies in-process duplicate protection, checks copier pause/subscription/broker eligibility, resolves channel metadata, and selects eligible brokers from the in-memory broker cache. For each broker, `sendOrder` first checks whether channel config is ready from cached broker state, then force-refreshes `broker_channel_trading_configs` through `fetchFreshBrokerForChannel(...)` before `withChannelTradingConfig(...)`, durable `claimSignalBrokerDispatch(...)`, and broker execution. Other live reads around this path include execution proof (`trades`, `signal_range_entry_waits`, `trade_execution_logs`), materialization/idempotency probes, range wait reads, and post-send signal finalization reads.
- **Read classification:** The repeated `broker_channel_trading_configs` row read is safe to cache briefly because it contains stable per-channel copier/manual/risk/layering/AI settings. `broker_accounts` are already cached in memory from startup + realtime. `telegram_channels` metadata is already cached by `channelMetaCache` and invalidated on channel updates. Copy-limit state already has its own short cache and was not moved into this feature. Durable claims, execution proof, idempotency/materialization checks, broker order state, current prices, open orders, broker connectivity/readiness, balance/equity/margin, kill switches, cancellation/reconciliation state, listener health ownership, and already-sent decisions remain explicitly excluded and live.
- **Implementation:** Added `worker/src/lightConfigCache.ts`, an in-memory per-worker cache around the pre-send `broker_channel_trading_configs` lookup. `LIGHT_CONFIG_CACHE_ENABLED=false` keeps the legacy database lookup path. When enabled, cache misses/expiry fetch the authoritative DB row, store a versioned entry, and apply the row to the broker before normal config resolution. Cached payloads are limited to the config row and recursively strip credential-like keys before storage. The final audit blockers were fixed before approval: stale in-flight fills are discarded after invalidation, invalidation uses structured exact identity instead of substring matching, and cache memory is bounded.
- **Entry shape / key:** Entries use `{ schemaVersion: 1, cachedAt, expiresAt, configVersionOrUpdatedAt, data }`, where `configVersionOrUpdatedAt` comes from `broker_channel_trading_configs.updated_at` when present. That field is informational only; it does not prevent stale writes. The stale-fill guard is the per-key generation/epoch. Keys are built from exact structured `{ userId, channelId, brokerAccountId }` identity with normalized channel ids and contain no secrets.
- **TTL / flags:** Defaults are `LIGHT_CONFIG_CACHE_ENABLED=false`, `LIGHT_CONFIG_CACHE_TTL_MS=5000`, and `LIGHT_CONFIG_CACHE_MAX_ENTRIES=1000`. Invalid TTL values fail safely by disabling cache use and reporting effective TTL `0`. Invalid max-entry values fall back to the safe default. Staging enablement requires setting `LIGHT_CONFIG_CACHE_ENABLED=true`, `LIGHT_CONFIG_CACHE_TTL_MS=5000`, and optionally keeping `LIGHT_CONFIG_CACHE_MAX_ENTRIES=1000`. Production must remain disabled until staging results are reviewed.
- **Invalidation:** `TradeExecutor.subscribeChannelTradingConfigs()` invalidates affected cache identities on `broker_channel_trading_configs` realtime before refreshing the existing broker cache. `INSERT` invalidates the new identity, `DELETE` invalidates the old identity, and `UPDATE` invalidates both old and new identities so broker/channel changes cannot leave the old cache key alive. When the broker owner is known in memory, invalidation is exact user+channel+broker; otherwise it falls back to a bounded structured broker+channel scan of known identities. No new Redis/pubsub subsystem was added; realtime invalidation plus the 5s TTL bounds staleness.
- **Stale-fill protection:** Each key has a generation counter. A DB fetch captures the current generation before it starts. Invalidation increments the generation and removes that key from the join map. If the old fetch later resolves, the caller may receive the DB result to preserve legacy semantics, but the result is not stored in cache and `light_config_cache_stale_fill_discarded` is counted. Newer generation fetches may populate normally, and failed fetches clear in-flight state.
- **Fallback behavior:** Valid hits use cached stable config. Misses, expired entries, malformed entries, invalid TTL, and disabled cache fetch DB. Cache subsystem errors are counted and bypassed; the wrapper falls back to the DB fetch. If the underlying authoritative DB lookup behaves as a no-row/no-update fallback, that existing behavior is preserved.
- **Safety boundaries:** The cache does not replace `ensureSignalRow`, `signalExecutionProven`, `manualDispatchAlreadyMaterialized`, `claimSignalBrokerDispatch`, broker session/readiness checks, broker symbol/quote/order calls, range wait state, cancellation state, reconciliation state, or post-send persistence. Cache failure must never stop trading/listening by itself, but required underlying DB failures preserve existing semantics.
- **Concurrency / memory:** The cache uses per-key singleflight. Concurrent identical user+channel+broker lookups await the same DB promise unless invalidation advances the generation; unrelated keys do not serialize. Completed and failed promises are removed. Entries are capped by `LIGHT_CONFIG_CACHE_MAX_ENTRIES` using deterministic recency/order eviction, and expired cold entries are pruned on get/set/invalidate without a high-frequency timer. At 50 users the default cap should be comfortably below limit for typical channel/account counts; at 500 users the hot set remains bounded; at 5,000 users hit rate may fall, but per-worker memory remains capped at 1000 entries unless explicitly tuned.
- **Metrics:** Added low-noise worker metrics for `light_config_cache_hit`, `light_config_cache_miss`, `light_config_cache_expired`, `light_config_cache_invalidated`, `light_config_cache_fallback_db`, `light_config_cache_malformed`, `light_config_cache_error`, `light_config_cache_singleflight_join`, `light_config_cache_stale_fill_discarded`, `light_config_cache_evicted`, `light_config_cache_pruned`, plus histogram-compatible lookup, cached-lookup, and DB-fallback duration metrics. Cache hit/miss/expiry does not emit Sentry issues.
- **Tests:** Added `worker/src/lightConfigCache.test.ts` covering disabled legacy behavior, first DB read, second hit within TTL, expiry/refetch, malformed entry refetch, cache failure fallback, DB failure semantics, exact invalidation, similar-id non-collision, update-style old/new invalidation, scoped fallback invalidation, unrelated entry retention, broker/risk setting changes not surviving beyond TTL, durable-claim/idempotency/broker-state/kill-switch/cancellation exclusions, duplicate-dispatch non-involvement, singleflight join, failed/successful inflight clearing, invalidation during inflight, cache-disable during inflight, multiple invalidations during inflight, max-entry eviction, cold expired pruning, 5,000 synthetic keys bounded to max, key separation, TTL/max-entry env diagnostics, config round-trip equivalence, metrics, and no secret storage.
- **Docs / env:** Added `docs/light-config-cache.md`, updated `docs/worker-deployment.md`, and added `LIGHT_CONFIG_CACHE_ENABLED=false`, `LIGHT_CONFIG_CACHE_TTL_MS=5000`, and `LIGHT_CONFIG_CACHE_MAX_ENTRIES=1000` guidance to `worker/.env.example`.
- **Staging rollout:** Deploy code with the flag off first. Enable only on staging trade workers with `LIGHT_CONFIG_CACHE_ENABLED=true`, `LIGHT_CONFIG_CACHE_TTL_MS=5000`, and `LIGHT_CONFIG_CACHE_MAX_ENTRIES=1000`. Measure reduced repeated config reads, lower config lookup p50/p95, correct realtime invalidation after settings changes, no stale broker/risk/layering settings beyond TTL, no stale-fill discard spikes after settings updates, no duplicate trades, unchanged durable claims/idempotency/kill-switch behavior, and no cache-caused broker failures.
- **Production-readiness pass:** The same artifact is intended to run in staging and production. Production deploys keep `LIGHT_CONFIG_CACHE_ENABLED=false`, preserving the legacy DB refresh path with no migration or persisted cache state. After staging approval, production enablement is configuration-only with the reviewed TTL/max-entry values. Rollback is also configuration-only: set `LIGHT_CONFIG_CACHE_ENABLED=false`; any in-memory entries are ignored by new dispatches and no DB/cache cleanup is required.
- **Production safety boundaries:** The cache scope remains only `broker_channel_trading_configs` and only the audited execution-relevant subset (`copier_mode`, `manual_settings`, `ai_settings`, `copy_limit_state`, `updated_at`). Durable claims, idempotency, duplicate execution proof, broker order state, prices, open orders, broker connectivity, balance/equity/margin, kill switches, cancellation/reconciliation state, listener health ownership, and anything proving an order was already sent remain live and uncached. A code comment at the integration point documents this boundary for future engineers.
- **Multi-worker behavior:** The cache is per-process volatile memory. Worker A and worker B do not share entries; realtime should invalidate each subscribed worker; missed invalidation is bounded by TTL; worker restart starts empty; shard/ownership movement does not copy cache state; no correctness assumption requires one global worker.
- **Settings-change guarantee:** Normal frontend, Edge Function, admin/backoffice, service-role, direct DB update, delete/recreate, broker disconnect/delete, and channel removal/unlink paths are expected to invalidate through `broker_channel_trading_configs` realtime when delivered. Do not claim universal instant invalidation: if realtime is missed or not delivered for a path, stale config is bounded by `LIGHT_CONFIG_CACHE_TTL_MS` (default 5s).
- **Production metrics / alerts:** Operational review should use hit rate `hit / (hit + miss)`, fallback rate `fallback_db / total lookups`, and error rate `cache_error / total lookups`. Warnings include cache error rate above 1% for 5 minutes, unexpectedly high fallback after warm-up, continuous stale-fill-discard spikes, hit rate near 0 for stable traffic, or sustained realtime/invalidation gaps. Disable cache immediately for any confirmed stale broker/account config use, duplicate trade, wrong risk config, execution outcome change, or cache exception reaching the broker hot path.
- **Staging acceptance gate:** Before production enablement, staging must show zero cache-attributable duplicate trades, zero stale broker selections, zero stale risk-setting incidents beyond TTL, zero claim/idempotency changes, zero kill-switch or broker-readiness bypass, zero cache-caused trade failures, fewer config reads, meaningful hit rate, improved config lookup p50, no p95/pre-broker regression, working invalidation/fallback/disable rollback, and memory within the configured bound. Use meaningful traffic: one internal account/channel first, then small cohort, then normal staging load.
- **Failure modes:** Disabled -> DB path; hit -> cached stable config; miss/expired/malformed/cache exception -> DB path; realtime missed -> stale bounded by TTL; invalidation during DB fetch -> stale completion discarded; cache full -> oldest/least-recent entry evicted; worker restart -> empty cache and DB warm-up; metrics failure -> execution unaffected; DB failure -> legacy DB failure semantics.
- **Security / privacy:** Cache keys contain no secrets and metrics do not label user/channel/broker ids. Cached values are in-process volatile memory only and must not contain broker passwords, API keys, access tokens, Telegram sessions, Supabase secrets, raw Telegram messages, raw broker payloads, balance, equity, or margin.
- **Rollback:** Set `LIGHT_CONFIG_CACHE_ENABLED=false` and restart/redeploy the trade worker. No migration, data cleanup, or code rollback is required.
- **Known risks:** Cross-worker invalidation depends on Supabase Realtime delivery; the 5s TTL is the safety bound if realtime is missed. The cache deliberately does not solve distributed caching or long-lived configuration reuse. Production enablement requires staging evidence.
- **Do not break these invariants:** (1) Cache off equals legacy behavior. (2) Only `broker_channel_trading_configs` is cached. (3) Durable claims are never cached. (4) Idempotency is never cached. (5) Broker order state is never cached. (6) Prices are never cached. (7) Kill switch remains live. (8) Broker readiness remains live. (9) Cache failure falls back safely. (10) DB failures preserve legacy semantics. (11) Stale entries are never served after expiry. (12) Realtime invalidation matches structured cache identity. (13) Invalidation during an in-flight DB fetch cannot resurrect stale config. (14) Same-key concurrent misses singleflight safely. (15) Failed fetch cannot permanently poison a key. (16) Cache cannot cause duplicate trade execution. (17) Cached and uncached data have equivalent execution semantics for current config fields. (18) No secrets are cached. (19) Memory cannot grow unbounded indefinitely. (20) Disabling the flag is a safe rollback.

### 2026-08-07 - Deferred Business Events + Accurate Copier Health

- **Branch:** `feat/deferred-events-copier-health`.
- **Relevant commits:** `064e3635` (`feat(observability): add deferred events and accurate copier health`) and `8c5e5124` (`fix(observability): complete deferred failure coverage`). No later local commits were present on this branch at the time this memory entry was written.
- **Context / objective:** This branch fixes two observability gaps before promotion from `dev`. First, several user-impacting failures happened after the main trade path had already reported success and were visible only in Railway/console logs. Examples include virtual pending materialization failure, broker-pending materialization failure, post-fill SL/TP failure, basket TP sync failure, management cleanup failure, and broker-success/database-persistence mismatch. Second, the dashboard previously inferred Live/Online mostly from lease freshness and Telegram session-row existence; neither proves that the Telegram listener is connected, MTProto is healthy, or signals are being processed.
- **Root cause - deferred events:** Fire-and-forget post-fill/background work often logged final failures only to console. These failures were not consistently represented as structured Sentry business events, so support had to search Railway logs to understand partial outcomes after a broker order succeeded.
- **Root cause - copier health:** `worker_session_leases` freshness represented listener ownership, not live MTProto/listener health. `telegram_sessions` row existence represented Telegram linkage, not active signal listening. Stale health could survive worker death, and the final audit also identified that old workers needed ownership-aware CAS hardening so they could not overwrite health now owned by a newer worker.
- **Deferred business-event implementation:** Added centralized structured business-event helpers for final deferred failures only. Successful follow-ups do not emit events; per-retry attempts do not emit events; capture is fire-and-forget; no Sentry capture affects trade outcome. A broker-success path remains successful even if later follow-up work partially fails, so the system records a partial/manual-review outcome instead of retroactively marking the successful broker order as failed.
- **Deferred event names to know:** `layering_materialization_failed`, `post_fill_follow_up_failed`, `stop_loss_update_failed`, `take_profit_update_failed`, `basket_tp_sync_failed`, `trade_management_cleanup_failed`, `broker_success_persistence_failed`, and `deferred_trade_follow_up_failed`.
- **Deferred reason codes to know:** `VIRTUAL_MATERIALIZATION_FAILED`, `BROKER_PENDING_MATERIALIZATION_FAILED`, `POST_FILL_SL_UPDATE_FAILED`, `POST_FILL_TP_UPDATE_FAILED`, `BASKET_TP_SYNC_FINAL_FAILURE`, `MGMT_CLOSE_CLEANUP_FAILED`, `BROKER_SUCCESS_DB_FAILURE`, `BROKER_PENDING_FILL_DB_FAILURE`, and `BASKET_RECONCILE_ENQUEUE_FAILED`.
- **Copier health implementation:** Added `copier_listener_health` persistence and a server-authoritative state model for Telegram account state, signal listener connectivity, copier engine status, and worker ownership. Worker health now records actual listener/MTProto connectivity, ownership identity, lease acquisition epoch, recent successful probe time, shutdown/recovery flags, freshness thresholds, and user-safe reason codes. Frontend status reads this health model instead of treating a fresh lease or session row as proof of operational readiness.
- **Health state model:** Telegram account states are `linked`, `not_linked`, `invalid`, and `reconnect_required`. Signal listener states are `connected`, `reconnecting`, `disconnected`, `failed`, and `unknown`. Copier engine states are `operational`, `degraded`, `offline`, and `stopped`. Worker ownership states are `owned`, `lease_expiring`, `unowned`, and `stale`.
- **Critical health rule:** Operational must not be inferred from a lease alone. Operational requires a valid linked session, active ownership, connected listener, `mtproto_connected=true`, a recent successful probe, a recent health row, no shutdown state, and no exhausted recovery.
- **Stale row safety:** Frontend and worker fail closed when `updated_at` is stale, `last_successful_probe_at` is stale, timestamps are missing/malformed, or ownership is stale. A stale row must never show Operational indefinitely.
- **Stale worker safety:** Health writes use ownership-aware CAS through `upsert_copier_listener_health(...)`. Stale owner writes return `stale_ownership`. Those failed health writes do not stop listener/trading. Old workers cannot overwrite health owned by a newer worker. Health persistence is operational metadata, not execution authority.
- **Grace period / write frequency:** `COPIER_HEALTH_OFFLINE_GRACE_MS=60000` by default. Short reconnects show degraded/reconnecting; reconnect/disconnect beyond grace becomes offline; exhausted recovery can fail faster; shutdown should not create a false critical outage. Health writes happen on meaningful state transition, and unchanged state writes are bounded to about 30-second intervals. There are no per-second DB writes, and health write failure does not affect trading/listening.
- **Frontend UX:** Dashboard status is separated into Telegram account, Signal listener, Copier engine, and Last healthy time. Normal users should not see MTProto, lease, shard, worker ownership, or heartbeat jargon. A Telegram session row can mean Telegram is linked, but it cannot make the signal listener Connected or copier engine Operational.
- **Sentry health behavior:** Only meaningful health issue events should be emitted, primarily `copier_engine_offline` and `telegram_listener_failed`. Do not emit issues for every health probe, lease renewal, brief reconnect, successful reconnect, or normal shutdown. Repeated failures use cooldown/grouping.
- **Migration:** Added `supabase/migrations/20260806120000_copier_listener_health.sql`. It is additive, enables RLS, lets authenticated users read only their own safe health state, prevents normal clients from writing worker health, uses service-role worker writes, adds ownership-aware CAS RPC, and stores no secrets/session strings. This memory update did not remotely apply the migration.
